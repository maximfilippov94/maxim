# Конструктор меню для нутрициологов — MVP

Сервис, где нутрициолог собирает меню для клиента из общей базы блюд, меняет
граммовку порций и видит КБЖУ по каждому приёму пищи и дню в реальном времени.
Клиент получает кабинет-PWA: отмечает съеденное, ведёт вес, пишет специалисту.

**Автогенерации меню нет.** Алгоритм только считает — решает специалист.

## Архитектура

**API-first.** Всё, что делает фронт, он делает через REST API `/api/v1/*`
(PHP, JSON, авторизация по Bearer-токену). Фронт (`/app`) — PWA на чистом JS без
сборки, потребляет тот же API, что и будущее нативное приложение.

```
nutrition/
├── config.php              конфиг (путь к БД, TTL сессий, окружение)
├── migrations/             нумерованные .sql-миграции
│   └── 001_init.sql
├── seeds/                  стартовые данные (общая база)
│   ├── ingredients.php     67 ингредиентов, КБЖУ на 100 г сырого
│   └── dishes.php          14 блюд из состава
├── bin/
│   ├── migrate.php         применение миграций
│   ├── seed.php            наполнение общей базы (идемпотентно)

├── src/
│   ├── Database.php        PDO-обёртка (SQLite + WAL, весь SQL через PDO)
│   ├── Router.php          роутер (~100 строк)
│   ├── Request.php / Response.php / HttpException.php
│   ├── Auth.php            Bearer-токены в таблице sessions
│   ├── Repo.php            переиспользуемые запросы + пересчёт кэша блюд
```

### Стек

- PHP 8.x без фреймворка
- SQLite в WAL-режиме (весь SQL через PDO, без SQLite-специфичных функций —
  миграция на PostgreSQL сводится к смене DSN)
- Фронт: чистый JS, mobile-first, нижняя навигация, крупные тач-таргеты
- PWA: manifest + service worker (кэш оболочки, оффлайн-показ последнего меню)

## Запуск

```bash
cd nutrition
php bin/migrate.php      # создать схему
php bin/seed.php         # наполнить общую базу ингредиентов и блюд
php -S 127.0.0.1:8000 -t public public/index.php
```

Открыть `http://127.0.0.1:8000/` → редирект на `/app/`.
Вход для специалиста, регистрация, дальше — клиенты и конструктор.
Клиент заходит по инвайт-ссылке `/app/#/invite/<token>` (кнопка
«🔗 Ссылка-приглашение» в карточке клиента).

Тесты расчёта КБЖУ:

```bash
php bin/test_calculator.php
```

## Логика расчёта КБЖУ (`NutritionCalculator`)

Единственное место, где рождаются ошибки — поэтому вся математика собрана в
одном классе, покрыта тестами и считается **только на бэке** (фронт может
показать предварительное значение, но правда приходит из API).

1. КБЖУ ингредиента — всегда на **100 г сырого** продукта.
2. КБЖУ блюда = сумма по составу. Базовый вес порции = сумма граммов состава
   с учётом `cooked_ratio` (готовый вес: рис ×2.5, мясо ×0.68…).
3. Порция масштабируется от базовой: `k = portion_g / base_portion_g`,
   `kcal_итог = kcal_блюда × k`.
4. При `overrides` (точечная правка граммовок ингредиентов) — пересчёт по
   составу с заменёнными граммовками, коэффициент масштабирования не применяется.
5. Итоги дня = сумма по всем пунктам; рядом — отклонение от целевых КБЖУ клиента.

| Метод | Путь | Роль |
|---|---|---|
| POST | `/api/v1/auth/specialist/register` \| `/login` | — |
| POST | `/api/v1/auth/client/login` | — |
| GET  | `/api/v1/invite/{token}` · POST `/accept` | — |
| GET  | `/api/v1/me` · POST `/auth/logout` | любой |
| CRUD | `/api/v1/ingredients` | специалист |
| CRUD | `/api/v1/dishes` (состав + автопересчёт КБЖУ) | специалист |
| CRUD | `/api/v1/clients` · POST `/{id}/invite` | специалист |
| CRUD | `/api/v1/menus` · POST `/{id}/publish` \| `/duplicate` \| `/copy-day` | специалист |
| CRUD | `/api/v1/menus/{id}/items[/{item_id}]` | специалист |
| POST | `/api/v1/menu-items/{item_id}/log` | клиент |
| GET  | `/api/v1/me/menu` \| `/menus` \| `/progress` | клиент |
| GET/POST | `/api/v1/me/messages` \| `/me/weight` | клиент |
| GET/POST | `/api/v1/clients/{id}/messages` · GET `/{id}/weight` | специалист |

## Экраны

**Кабинет нутрициолога:** список клиентов (цель, статус меню, непрочитанные),
карточка клиента (анкета, целевые КБЖУ, история меню, чат, вес), **конструктор
меню** (дни-табы, приёмы пищи, добавление блюда в 2 тапа, слайдер граммовки,
липкая плашка итогов дня с отклонением от цели, копирование дня и дублирование
меню), база блюд с поиском/фильтрами и созданием блюд из ингредиентов.

**Кабинет клиента:** «Сегодня» (меню дня, отметки «съел/пропустил», итоги),
«Неделя» (все дни), карточка блюда (состав, рецепт, КБЖУ, комментарий),
«Прогресс» (кольцо соблюдения, ввод и график веса), чат.

## Юридический контур

Сервис — инструмент планирования питания, не медицинская услуга. В анкете
клиента показан дисклеймер о необходимости консультации врача при беременности,
диабете, заболеваниях ЖКТ и РПП. Для продакшена: оферта, согласие на обработку
ПДн (152-ФЗ), хостинг в РФ.

## Дополнительные модули (сверх базового MVP)

- **Анкета клиента при старте** — клиент по инвайту сам заполняет цель, вес,
  активность, аллергии, предпочтения и медицинские флаги (беременность, диабет,
  ЖКТ, РПП) с дисклеймером. Нутрициолог видит анкету в карточке клиента;
  целевые КБЖУ по-прежнему задаёт специалист. (`GET/PATCH /api/v1/me/intake`)
- **Профиль нутрициолога + публичный каталог** — специалист заполняет страницу
  (фото, специализация, опыт, город, цена, регалии) и опционально включает показ
  в каталоге. Публичные страницы без авторизации: каталог с поиском и рейтингом,
  страница специалиста по ЧПУ-slug. (`GET /api/v1/catalog`, `/catalog/{slug}`,
  `GET/PATCH /api/v1/profile`)
- **Отзывы и рейтинг** — клиент оценивает своего специалиста (1–5 + текст),
  средний рейтинг агрегируется в каталоге. (`GET/POST/DELETE /api/v1/me/review`)
- **Рецепты по шагам + фото** — у блюда пошаговый рецепт (чекбоксы «шаг готов»)
  и фото; загрузка изображений через `POST /api/v1/uploads/image`.
- **Список покупок** — автоматически из состава всех блюд меню (или диапазона
  дней), с группировкой по категориям и отметками «куплено» (локально у зрителя).
  (`GET /api/v1/menus/{id}/shopping-list`)

Схема этих модулей — в миграции `002_profiles_recipes_intake_reviews.sql`.
